Vocabulary

Microkernel
One low-level GPU shader running one matrix multiplication. This report does not measure the full LLaMA model directly.
GEMM shape
A[M,K] @ B[K,N] = C[M,N]. For prefill S=128, M=128; K is input width; N is output width.
Q8CSW
Non-coopmat int8 weight path: 8-bit weights, fp16 activations. Also called W8A16 here. It saves weight bandwidth, but still pays scalar dequantization cost.
W8A8
8-bit weights and 8-bit activations. Both matmul inputs are int8, enabling true int8 dot-product or cooperative-matrix math.
Q8TA
W8A8 non-coopmat shader using packed int8 dot-product instructions. It is much faster than Q8CSW and beats int8 coopmat on smaller Q/O and K/V shapes.
CM wave64
Corrected int8 cooperative-matrix shader for AMD wave64 hardware. It is the fast tensor-core-like path for large FFN shapes; the older wave32-assumed shader was invalid on the 780M.
FFN gate/up
Two FFN projections with shape (128,4096,14336), appearing 64 times per forward. This is the largest repeated output width, so int8 CM wins here.
FFN down
FFN projection back to hidden size, shape (128,14336,4096), 32 dispatches. Int8 CM wins, but less strongly than gate/up.
Q/O
Attention query and output projections, shape (128,4096,4096), 64 dispatches. Q8TA is faster than int8 CM because CM tile overhead is too high here.
K/V
Attention key and value projections, shape (128,4096,1024), 64 dispatches. Small output width launches too few CM workgroups, so Q8TA is better.

Main Answer

Int8 coopmat is the right path for large FFN matmuls, but it is not the right path for every linear.

Recommended int8 strategy: use KHR coopmat for FFN-sized projections and q8ta for smaller attention projections.
The old wave32 numbers are invalid on the 780M because the shader did incomplete work under wave64.

int8 Coopmat vs int8 No Coopmat

There are two useful no-coopmat int8 baselines. q8csw is W8A16: int8 weights with fp16 activations and scalar dequantization. q8ta is W8A8: int8 weights and int8 activations using packed int8 dot-product instructions, but not cooperative matrix.

Against q8csw, int8 coopmat wins everywhere because it avoids much of the W8A16 scalar dequant bottleneck. Against q8ta, int8 coopmat wins only for FFN because q8ta is already a strong W8A8 int8-dot-product path.

Performance Analysis: Why Some int8 Coopmat Cases Are Slower

Cause What happens Where it shows up
Low workgroup count K/V has M=128, N=1024, and a 128x128 tile, so it launches only 1 x 8 = 8 workgroups. K/V leaves part of the 12-WGP GPU idle.
Fixed tile overhead Coopmat pays shared-memory prefetch, barriers, cooperative matrix load/store, and output tile setup per workgroup. At Q/O and K/V, setup cost is a large fraction of latency.
Tile shape mismatch The wave64 shader is built around a 128x128 output tile. FFN gate/up has 112 tiles across N; K/V has only 8. FFN amortizes overhead; K/V does not.
q8ta is a strong baseline q8ta is W8A8 and uses packed int8 dot-product instructions with lower setup overhead than coopmat. q8ta beats coopmat at Q/O and K/V.
q8csw is a weaker baseline q8csw is W8A16 and pays scalar dequantization cost while multiplying int8 weights with fp16 activations. coopmat beats q8csw even at smaller shapes.
The slow cases are overhead and occupancy problems, not proof that int8 math is slower. The fast int8 matrix instruction only helps when enough tile work exists to amortize the surrounding shader machinery.

Practical Conclusion

The corrected wave64 int8 coopmat path is worth using for FFN, but routing every LLaMA linear through it would leave performance on the table. The best short-term path is a hybrid dispatcher: coopmat for large-N FFN shapes and q8ta for smaller attention projections. The remaining work is integration and W8A8 export, not more tuning of the same tile-schedule knobs.
